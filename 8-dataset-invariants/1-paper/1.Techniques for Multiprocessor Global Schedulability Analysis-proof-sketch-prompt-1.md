### GPT Polish:
ROLE
Assume the role of a real-time systems researcher and Prosa/Coq expert with high code-quality standards.

INPUT
You will be given (or have) a schedulability paper with multiple theorems.

OBJECTIVE
1) Extract only the parts of the paper that can be mechanized and proved in Coq using Prosa.
2) Produce BOTH:
   A) a concise, ordered, step-by-step plan/checklist to mechanize the proofs in Prosa/Coq, and
   B) a single-file Coq/Prosa skeleton that contains ONLY comments (no executable code), showing where each definition/lemma/theorem will go and what to do there.

SCOPE & CONSTRAINTS
- Include ONLY sections that will be converted into a mechanized Coq/Prosa proof of the paper’s main theorems. Omit optional sections or corollaries that are not needed or cannot be fully mechanized.
- Treat everything as a single file (no multi-file layout).
- In the skeleton, DO NOT write imports, definitions, tactics, or any Coq code. Use comments only.
- Modularize aggressively: make building blocks as unit/small as possible.
- Use the exact comment delimiter “====section====” to mark major sections and subsections.
- Use programming-standard variable names (e.g., snake_case; no Greek letters or symbols). Provide a short symbol-to-identifier mapping inside comments when needed (e.g., “paper’s τ_i -> task_i”).
- Align with Prosa concepts where applicable (tasks, arrivals, schedulers, interference, response time, busy intervals, etc.), but still keep everything comments-only in the skeleton.

WHAT TO ANALYZE & DECIDE
- Identify workload, resource, scheduler, and analysis assumptions that MUST be formalized.
- List all theorems/lemmas actually needed for the main results and map their dependencies.
- Specify which definitions/invariants must be introduced to bridge the paper and Prosa.
- Propose helper lemmas and intermediate results required to reach each theorem.
- Exclude anything not essential to proving the main theorems mechanistically.

OUTPUT FORMAT
Produce two parts:

PART A — Mechanization Plan (Checklist)
- A numbered, minimal-to-maximal dependency order of actions a Prosa/Coq script writer should follow.
- Each step should say exactly what to formalize, which Prosa concept it maps to, and what intermediate lemmas are needed.
- Keep it concise, actionable, and sequential.

PART B — Single-File Coq/Prosa Skeleton (Comments-Only)
- Output as a single code block.
- Use only comments; no code at all.
- Start with a brief commented “Symbol Mapping” section for variable naming (paper notation -> program-safe identifiers).
- Then structure the rest with “====section====” markers, e.g.:
  (*
    ====section==== Paper Assumptions & Model Bridges
    - What: define (in real code later) task model, arrival curves, WCETs, deadlines, platform, scheduler.
    - How: explain which Prosa records/types these will map to.
  *)
  (*
    ====section==== Core Definitions Needed
    - What: state each definition to be introduced (as comments).
    - Why: explain how it’s used by later lemmas.
  *)
  (*
    ====section==== Helper Lemmas
    - For each lemma: a comment block with
      - Inputs (named with program-safe identifiers),
      - Intended statement in prose,
      - Sketch of the proof strategy (case splits, induction measure, key Prosa facts to apply).
  *)
  (*
    ====section==== Main Theorems
    - For each theorem: a comment block with
      - Preconditions/assumptions,
      - Goal (schedulability bound/response-time theorem/etc.),
      - Calls to prior lemmas (by name) and the composition logic,
      - Final proof outline.
  *)
- Keep blocks small/unit-sized and clearly labeled.

STYLE
- Be precise, terse, and implementation-oriented so a Coq developer can follow the checklist and then fill in the code where each comment says.
- Do not include any narrative not directly supporting mechanization.

NOW DO IT
Using the paper’s content, produce PART A (the ordered checklist) and PART B (the single-file comments-only Coq skeleton with “====section====” markers and program-safe identifiers).
